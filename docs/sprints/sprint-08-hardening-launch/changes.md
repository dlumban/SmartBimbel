## Task 8.1 — End-to-End Testing & QA Pass

**Web (Playwright), API-level + real browser.** The real constraint driving this task's design: `apps/web`'s login state is 100% driven by the real Firebase client SDK (`onAuthStateChanged` in `useAuth.tsx`; `lib/api.ts`'s `apiFetch` pulls a fresh token from `firebaseAuth.currentUser.getIdToken()` on every call, with no persisted session). Since no real Firebase project exists in this environment, a real browser cannot get past login through the actual UI. Presented with this, the user chose **API-level E2E instead of retrofitting a frontend auth bypass** into production code (the alternative would have meant shipping a test-only login seam into `useAuth.tsx`/`lib/api.ts` themselves — a materially bigger, more security-sensitive change than a server-side-only bypass).

- `services/api/src/auth/firebase-admin.service.ts` — added a narrowly-scoped E2E auth bypass: `verifyIdToken()` accepts a token in the form `E2E.<base64url-json>` in place of a real Firebase ID token, decoding `{secret, uid, email?, phone_number?}` and returning a decoded-token-shaped object, but **only** when `E2E_AUTH_BYPASS_SECRET` is explicitly set (unset in every real `.env`, never in production) **and** `NODE_ENV !== "production"` **and** the token carries the matching secret. Any token not starting with `E2E.` falls through to real Firebase verification untouched. Mirrors exactly what the Jest e2e suite already does by mocking this same method — just made reachable over HTTP for a live server process, which Playwright needs and Jest's DI-override doesn't. 6 new unit tests in `firebase-admin.service.spec.ts` cover: no bypass without the secret, no bypass without the `E2E.` prefix, no bypass when `NODE_ENV === "production"` even with a valid token, wrong-secret rejection, malformed-token rejection, and the happy path.
- `apps/web/e2e/` (new): `helpers.ts` (token building, session registration, and a Postgres-direct cleanup routine scoped to a `e2e-pw-` firebaseUid prefix so it can never touch real/seed data), `global-setup.ts`/`global-teardown.ts` (idempotently create/remove one real availability slot on the seeded, already-VERIFIED tutor via `POST /tutors/me/availability` — `prisma/seed.ts`'s tutors ship with zero `AvailabilitySlot` rows, and onboarding a whole new tutor was out of scope), `public-pages.spec.ts` (real Chromium browser: landing page, tutor discovery, city-filtered search, tutor detail page, and the unverified-tutor-invisibility edge case against the real seeded data — Tono Pratama/PENDING and Dewi Lestari/REJECTED are absent), `happy-path-api.spec.ts` (drives the real live server via HTTP: registration → role selection → profile completion → discovery → booking request → tutor accept → payment-initiation correctly reports unavailable, since Midtrans isn't configured in this environment — the same thing a real user hits today; plus a tutor-decline edge case), `concurrent-booking.spec.ts` (fires two real simultaneous HTTP requests for the same slot+occurrence from two different students — confirms `bookings.service.ts`'s `FOR UPDATE` row lock actually holds under real concurrent load: exactly one `201`, one `400` with "no longer available", from Sprint 3 Task 3.2's own edge-case note).
- **What this suite does not reach, and why**: the pay → webhook → `CONFIRMED` transition needs a deterministic fake Midtrans, which only exists as a Jest `TestingModule` DI override (`overrideProvider(MidtransService)` in `payments-webhook.e2e-spec.ts`) — not reachable from outside the process, so a live-server Playwright run genuinely cannot fake it without real Midtrans sandbox credentials. Everything past that point — chat, session completion, review, payment failure/retry, dispute+refund — is already covered functionally by the existing Jest e2e suite (`payments-webhook.e2e-spec.ts`, `sessions-reviews.e2e-spec.ts`), just not duplicated here. This is a real environment constraint, not a scope cut.
- **Not built at all**: Flutter/mobile integration tests and manual Android device QA — no mobile app exists in this project (web + admin only, confirmed by the repo's actual directory structure), so this AC is inapplicable rather than deferred.

## Task 8.2 — Performance Optimization & Load Testing

- **Database query review**: indexes on `TutorProfile.city`/`verificationStatus`/`hourlyRate` (Task 0.4/2.1) confirmed present. `EXPLAIN ANALYZE` against a synthetic ~2,000-row tutor dataset (seeded temporarily, cleaned up immediately after — verified via the `tutors`/`discovery` e2e suites that the DB returned to its expected clean state) showed Postgres correctly choosing a sequential scan for low-selectivity filters (e.g. `verificationStatus`, where most rows match) and correctly using the index for a narrow, selective filter (a single city). Both are correct planner behavior, not a missing-index bug — a sequential scan on a filter that matches most of the table is what a healthy query planner is supposed to do.
- **Frontend bundle audit** (`apps/web`, production build): every route is 88–150 kB first-load JS except `/bookings/[id]/chat` at **662 kB**, entirely `stream-chat-react` (Task 4.1). This is contained by Next's automatic route-based code splitting — no other page pays that cost — which is the right place for a rich chat UI library to live. **`next/image` migration** (2 files use plain `<img>`: `TutorCard.tsx`, `TutorDetailView.tsx`) was evaluated and **deliberately deferred**: `next.config.js` has no `images.remotePatterns` configured, and `photoUrl` is null for every real profile in this environment (no image storage/CDN backend is provisioned — `STORAGE_PROVIDER=local`, see `docs/third-party-setup.md`). Configuring `next/image` against a storage backend that won't be the real production one would be throwaway config; revisit once a real image CDN is chosen.
- **API load testing** (`services/api/test/load/`, k6 — installed locally, not a project dependency): `k6-tutor-search.js` (discovery, the highest-traffic read endpoint) and `k6-booking-create.js` (the highest-value write endpoint, using the same E2E auth bypass Playwright's suite uses). **Real finding**: `app.module.ts`'s global `ThrottlerGuard` (100 req/min per IP, Task 8.3) correctly rate-limits a burst from a single machine — a 100-VU ramping-load run against `/tutors` measured mostly `429`s, which is the throttle working as designed, not a performance bug. This makes genuine multi-thousand-concurrent-user throughput testing impossible from a single dev machine (every real production client has its own IP and its own 100/min budget; a single-origin load generator does not) — that needs either a distributed load generator or a staging deployment, both outside this engineering session's reach. What's captured instead is real, unthrottled per-request latency: tutor search averaged **6.3 ms** (p95 9.2 ms) and booking creation — a full DB transaction with a row lock, notification write, and BullMQ enqueue — averaged **54.6 ms** (p95 113 ms), both against the local dev Postgres/Redis. `cleanup-load-test-data.ts` removes everything either script creates.
- **4G network throttling test**: `apps/web/e2e/network-throttling.spec.ts`, run separately via `pnpm test:e2e:perf` (needs a **production** build — `next dev`'s unbundled/unminified JS made an early run of this same test show ~23s, a dev-mode artifact, not a real number). Against `next build && next start` with real Chrome DevTools Protocol network emulation (Lighthouse's "Slow 4G" profile: 1.6 Mbps down / 750 Kbps up / 150 ms RTT), the tutor discovery list loaded in **2.28s** — under PRD §7's 3-second target, with real evidence rather than an assumption.
- **Not built**: Flutter app cold-start profiling — no mobile app exists in this project.

## Task 8.5 — Analytics & Error Monitoring

Both integrations follow the same gated-SDK pattern already established for Midtrans/Stream Chat: real SDK wired, activates only when real credentials are configured (none are, in this environment).

- **Sentry**: `@sentry/node` in `services/api` (`monitoring/sentry.ts` + `SentryExceptionFilter`, reporting every unhandled 5xx — 4 passing unit tests), `@sentry/nextjs` in both `apps/web` and `apps/admin` (`sentry.client/server/edge.config.ts` + `instrumentation.ts`, gated behind `experimental.instrumentationHook` in `next.config.js`). Confirmed inert (clean startup log: "SENTRY_DSN not set - error monitoring is disabled") and confirmed it doesn't break a production build either way.
- **Firebase Analytics**: `apps/web/src/lib/analytics.ts` — `trackEvent()` wired into the funnel PRD/Task 8.5 names: `sign_up`/`login` (`LoginForm.tsx`), `role_selected` (`RoleSelector.tsx`), `booking_requested` (`NewBookingForm.tsx`), `begin_checkout` (`PaymentSection.tsx`), `review_submitted` (`ReviewSection.tsx`). Fully defensive by necessity — every call site fires it unawaited (`void trackEvent(...)`) from a user-facing action handler, so it must never be able to throw into or block that action; wrapped in try/catch with `.catch(() => null)` on the `isSupported()` chain. 4 passing unit tests.
