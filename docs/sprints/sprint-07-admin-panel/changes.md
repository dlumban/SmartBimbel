# Sprint 7 — Changes Log

Status: **Complete**. All 6 tasks built and verified. Unlike Sprints 4-6, nothing here is gated behind a missing third-party credential — this sprint formalizes access control and builds a genuinely new application (`apps/admin`) over data and endpoints that already existed from earlier sprints, so everything described below is fully live and end-to-end tested.

## Task 7.1 — Admin Panel Foundation & RBAC

- `AdminRole` enum (`SUPER_ADMIN`, `SUPPORT`) added to `User` - meaningful only when `role === "ADMIN"`, matching Sprint 1's precedent that admin accounts are bootstrapped directly (never self-service). `AdminRoleGuard` + `@AdminRoles(...)` is a second, opt-in guard layered on top of the existing `RolesGuard`/`@Roles("ADMIN")` check - routes with no `@AdminRoles()` decorator are open to either sub-role (matches PRD §5's "Support: user/booking/dispute handling"); only payout approval, manual booking override, and admin-role management require `SUPER_ADMIN` ("financial approval rights" from the task's own scope).
- `AuditLog` model (append-only, `adminUserId`/`action`/`targetType`/`targetId`/`metadata`/`createdAt`) - every admin-mutating action across every module this sprint touches calls `AuditLogService.log()` immediately after the real mutation succeeds (never inside the same transaction, so a logging hiccup can't roll back a legitimate action): tutor verify/reject, payout status change, dispute resolution, user suspend/reinstate/admin-role-change, and manual booking override. `GET /internal/audit-log` (either sub-role) lets support staff answer "who did what, when" without a direct DB query.
- `apps/admin`: real Next.js app (previously a bare Sprint 0 scaffold) - `AuthProvider`/`useAuth` mirrors `apps/web`'s pattern exactly (same `POST /auth/session` exchange), but `AdminShell` additionally redirects anyone whose session isn't `role: "ADMIN"` straight to `/login`, and `AdminLoginForm` has no self-registration path (unlike `apps/web`'s `LoginForm`) - admin accounts are never created by signing up.
- **Real gap found and fixed while building Task 7.2's document review**: no admin-facing endpoint existed to view a pending tutor's uploaded KTP/diploma - the only document-download route (`GET /tutors/me/documents/:type`, Sprint 1) was self-service-only. Added `GET /internal/tutors/:id/documents/:type`, served the same authenticated-buffer way (never a public URL), so Task 7.2's AC ("review documents without leaving the panel") is actually satisfiable.

## Task 7.2 — Tutor Approval Workflow UI

- `TutorApprovalQueue`: replaces the Task 1.6 Prisma-Studio-or-bare-page stopgap with a real two-pane review screen (queue + selected profile detail, including the new document links). Approve is one click; reject requires a reason (enforced client-side before the call, and server-side regardless per the existing `VerifyTutorDto`).
- No new backend logic was needed for approve/reject/resubmit-reappears-in-queue - `TutorsService.verify()`/`listPendingReview()` (Sprint 1) already did the right thing; this task only added the UI and the document-viewing gap fix above, plus audit logging on `verify()`.

## Task 7.3 — User & Booking Management

- `AdminUsersController`/`AdminUsersService` (`/internal/users`): search by role/status/name/email/phone, detail view (profile + booking/transaction counts), suspend/reinstate (either sub-role - toggles `User.status`, which `FirebaseAuthGuard` already rejects at the auth boundary, Sprint 1), and Super-Admin-only admin-role management (only ever changes the sub-role of an existing `ADMIN` account, never promotes a Student/Tutor).
- `AdminBookingsController`/`AdminBookingsService` (`/internal/bookings`): platform-wide search (status/city/subject/date-range/name) and detail with **no participant-membership check** (unlike the student/tutor-facing `BookingsService.findOne`) - support staff need to look up any booking. Manual override-cancel is Super-Admin-only, rejects an already-terminal booking, and reuses the existing `cancelledByUserId`/`cancellationReason` fields (an admin override is recorded the same way a participant cancellation is, just attributed to the admin) rather than adding new schema.
- **Real bug found and fixed**: `reportNoShow` was `ACCEPTED`-only until this session; separately relevant here because the same "which statuses count as active/terminal" question came up for override-cancel - `TERMINAL_STATUSES` (`DECLINED`/`EXPIRED`/`CANCELLED`/`COMPLETED`) was defined once and gets this right from the start.

## Task 7.4 — Transaction & Payout Management

- `AdminTransactionsController`/`AdminTransactionsService` (`/internal/transactions`): read-only list (either sub-role) plus a reconciliation view. Without live access to Midtrans's own transaction-status API (no credentials exist in this environment, the same gate as every other Midtrans touchpoint since Sprint 5), the reconciliation heuristic flags any `PENDING` transaction older than the documented `PAYMENT_WINDOW_HOURS` (24h) - by then it should have either been confirmed by webhook or expired by `PaymentExpiryProcessor`; still `PENDING` past that point means a webhook delivery gap or a stuck job, worth a human look. Explicitly documented as the best available signal given the constraint, not a claim of real-time gateway reconciliation.
- `AdminPayoutsController` (existing, Sprint 5) updated: `PATCH .../status` is now `@AdminRoles("SUPER_ADMIN")`-gated and audit-logged. `PayoutsQueue` shows the pending queue to both sub-roles (a Support admin sees a clear "you can view but not process" notice) but only renders the action buttons for a Super Admin - the real gate is server-side either way.

## Task 7.5 — Dispute Resolution Tools

- `AdminDisputesController` (existing, Sprint 5) - `resolve()` now audit-logs every resolution. `DisputesQueue` shows full context per the task's AC (both parties' names, booking status, the no-show flag from Sprint 3, and the linked transaction's status) plus an SLA age label (`ageLabel()`), so support staff never need to query the database directly.
- `AdminReportsController` (new, `/internal/reports`) surfaces Sprint 4's `MessageReport` rows - reported messages/users are visible and cross-referenced by `bookingId` even when not tied to a formal dispute, per the task's own scope note. One-click "escalate report to dispute" was **not** built (a support admin can already open the referenced booking and raise/resolve a dispute manually, or suspend the reported user via Task 7.3's tooling) - the content is genuinely visible and actionable through the existing tools, just not fused into a single button; noted here rather than silently scoped out.

## Task 7.6 — Analytics Dashboard

- `AnalyticsService` computes every metric in PRD §3's table directly from the platform's own DB (never the separate Firebase Analytics/Mixpanel product-usage tooling from Task 0.6): registered tutors/students, completed bookings, booking conversion rate (requested → confirmed/completed), GMV and platform take (from `PAID`/`REFUNDED` transactions' `paidAt`), average session rating (non-flagged reviews only, matching Task 6.5's own exclusion rule), tutor activation rate (≥1 completed booking / all verified tutors), and student second-booking rate.
- Date-range filtering is applied consistently to every count via whichever timestamp best represents "when this metric's event happened" (registration date, completion date, payment date) - documented per-metric in code since PRD doesn't pin an exact field, which is what makes the AC ("date-range filtering correctly recomputes all widgets") actually true rather than partially true. One deliberate exception: `tutorActivationRate`'s denominator (currently-verified-tutor count) is a snapshot, not range-scoped - scoping it too would make an early, short date range look artificially healthy.
- `GET /internal/analytics/cities` groups bookings/GMV/platform-take by the tutor's registered city, satisfying PRD §1/§3's multi-city framing.
- `AnalyticsDashboard` (web): 9 metric cards, 7/30/90-day presets plus custom date range, and a city breakdown table.
